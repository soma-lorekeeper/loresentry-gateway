# 프론트 인증 연동 인계

> **책임:** 프론트의 로그인 확인·동의 화면·온보딩·회원 탈퇴·오류 처리·탭 간 인증 전환 조율을 정한다.
>
> **확인할 때:** 프론트에서 인증 상태와 진행 중인 API 요청을 관리할 때.

단일 세션 ID 방식의 프론트 연동 계약이다.
브라우저는 HttpOnly 쿠키만 사용하고 ID를 JavaScript·localStorage·응답 JSON에서 읽지 않는다.

## 요청과 로그인

- API 주소는 [환경별 브라우저 설정](BROWSER_SECURITY.md#환경별-설정)을 따른다.
- API 요청에는 `credentials: "include"`를 적용하고 사용자 ID 헤더를 인증 수단으로 보내지 않는다.
- POST·PUT·PATCH·DELETE에는 `X-LS-CSRF: 1`을 추가한다. 로그아웃도 동일하다.
- 로그인은 `GET /auth/oauth/google/prepare`로 페이지 이동한다.
- 고정 `/login?result=...` 복귀 뒤 `GET /auth/users/me`로 실제 로그인을 확인한다.
  result는 화면 안내 값이며 인증 근거가 아니다.

## 약관 동의

로그인 화면에서 동의 모달을 표시한다. `result=terms_required`로 복귀한 경우에는 위 본인 계정
조회에 앞서 [약관 조회 API](API.md#약관-동의-api)를 호출한다. 결과 표식이나
쿠키 존재를 로그인 성공으로 간주하지 않고, API가 대기를 확인했을 때 원문을 표시한다.
브라우저는 HttpOnly 쿠키를 직접 읽지 않는다.

체크박스는 미선택 상태로 시작하며 다음 문구와 개인정보 처리방침 열람 링크를 제공한다.

> **[필수] Lore Sentry 서비스 이용약관에 동의합니다.**
>
> 개인정보 처리방침 보기
>
> 약관에 동의해야 로그인을 완료하고 서비스를 이용할 수 있습니다.

약관 제목·전문은 API로 받은 일반 텍스트로 표시한다. 링크만으로 전문을 대체하지 않는다.
신규·기존 회원 모두 버튼은 **“동의하고 계속”**이며 체크 전이나 제출 중에는 비활성화한다.
완료 요청에는 화면에 표시한 `terms_version_id`만 보내고, 내부 대기 식별자는 보내지 않는다.
`204`를 받으면 기존 로그인 완료 절차대로 본인 계정을 조회한 뒤 서비스로 이동한다.

| 상황 | 화면 처리 |
|---|---|
| 모달 닫기 | 서버 요청 없이 닫고 URL의 결과 표식을 제거. 로그인 화면에 머물며 즉시 다시 열지 않음 |
| 탭 닫기 | 서버 요청 없음. 별도 취소·쿠키 삭제를 시도하지 않음 |
| `result=terms_required` 화면 재진입·새로고침 | 약관 조회로 대기를 확인하고 유효하면 모달 표시 |
| 일반 로그인 화면 재진입 | 대기를 자동 조회하지 않음. Google 로그인부터 다시 시작 가능 |
| `CONSENT_REQUEST_INVALID` | 모달을 종료하고 Google 로그인 재시작 안내 |
| `TERMS_VERSION_MISMATCH` | 최신 원문 재조회·체크 해제 후 사용자에게 다시 동의받음 |
| `LOGIN_UNAVAILABLE`·통신 실패·잘못된 응답 | 실패 또는 결과 확인 불가 안내 후 로그인 재시작. 완료 요청 자동 재전송 금지 |

동의 대기 중에는 새 로그인 세션이 없으므로 이 흐름만으로 서비스에 진입할 수 없다.
원문 조회 실패나 새 원문 표시 후 이전 체크 상태로 자동 제출하지 않는다.

## 온보딩 상태

본인 계정 응답의 `onboarding_completed`로 첫 진입 온보딩 표시 여부를 정한다. 기존 회원은
`true`로 시작하며 신규 가입 계정만 `false`다. 로컬 저장소의 표시 기록을 기준으로 삼지 않는다.

- `false`이면 로그인 확인 뒤 온보딩을 표시한다.
- 사용자가 온보딩을 끝내거나 건너뛰면 `PUT /auth/users/me/onboarding`을 본문 없이 호출한다.
  `204`를 받으면 화면의 계정 상태를 `true`로 바꾼다. 반복 호출해도 결과는 같다.
- 완료 기록이 `ACCOUNT_UNAVAILABLE`·통신 오류로 실패해도 화면 진행을 막지 않는다. 다음 로그인 확인에서
  `false`가 유지되면 다시 표시될 수 있다. 자동 반복 재전송은 하지 않는다.
- 도움말의 온보딩 다시 보기는 프론트 화면 동작이며 서버 상태를 바꾸지 않는다.

샘플 프로젝트가 필요하면 `POST /projects/sample`을 본문 없이 호출한다. 응답·Location·오류는
프로젝트 생성과 같으며, 결과가 불명확한 실패 뒤에는 프로젝트 목록을 다시 조회해 중복 생성을 피한다.

## 회원 탈퇴

탈퇴 화면은 삭제 범위(계정·Google 연결·동의 기록·모든 프로젝트와 원고·설정·이미지)와 즉시
삭제·복구 불가를 안내하고, 사용자가 계정 이메일을 직접 입력한 뒤에만 제출을 허용한다.
`POST /auth/users/me/deletion`에 `{"confirmation_email": "<입력값>"}`만 보낸다.
제출 중에는 버튼을 비활성화하고 다른 보호 요청·자동 폴링을 멈춘다.

| 결과 | 화면 처리 |
|---|---|
| `204` | 쿠키 삭제가 적용된 것으로 보고 모든 탭에 인증 종료를 알린 뒤 로그인 화면으로 이동. 계정 재조회 불필요 |
| `ACCOUNT_CONFIRMATION_MISMATCH` | 입력란 오류 표시. 아무것도 삭제되지 않았음 |
| `INVALID_REQUEST` | 요청 구성 결함. 일반 오류 안내 |
| `ACCOUNT_DELETION_UNAVAILABLE` | 일부 데이터가 이미 삭제됐을 수 있음을 알리고 사용자가 다시 시도하도록 안내. 자동 재전송 금지 |
| `UPSTREAM_INVALID_RESPONSE`·통신 실패 | 결과 확인 불가 안내. 재시도 가능 |
| `SESSION_INVALID`·`SESSION_REQUIRED` | 재시도 중 이 결과면 이전 요청에서 탈퇴가 완료됐을 수 있음. 로그인 화면으로 이동 |
| `USER_NOT_FOUND`·`USER_CONTEXT_REQUIRED` | 재로그인 안내 |

`503` 뒤 재요청은 안전하다. 이미 삭제된 단계는 같은 결과로 넘어간다. 탈퇴 후 같은 Google 계정으로
다시 로그인하면 신규 가입으로 처리되어 약관 동의와 온보딩을 다시 거친다.

## 활동과 만료

보호 요청의 인증 성공마다 [세션·쿠키 수명](BROWSER_SECURITY.md#세션-쿠키)이 연장된다.
화면만 열어 두거나 입력만 하는 것은 활동으로 계산되지 않는다. 로그인 유지를 위한
heartbeat를 추가하지 않는다. 실제 보호 API 폴링은 활동으로 계산된다.
인증에 성공한 뒤 도메인 오류가 발생한 요청도 세션은 연장될 수 있다.

브라우저의 쿠키 차단·삭제·보관 제한이나 응답 유실이 서버 TTL과 다른 로그아웃 시점을
만들 수 있다. 서버가 ID를 유효하게 검증한 결과를 최종 기준으로 삼는다.

## 오류 처리

`SESSION_REQUIRED`·`SESSION_INVALID`는 보호 작업을 중단하고 재로그인으로 안내한다.
`SESSION_UNAVAILABLE`는 일시 장애로 처리하며 사용자 상태를 즉시 로그아웃으로 바꾸지 않는다.
401·503·네트워크 오류의 원래 요청을 일괄 자동 재전송하지 않는다. 특히 저장·수정은 결과
유실 가능성이 있으므로 각 도메인의 중복 방지 계약을 따른다.

## 인증 전환과 늦은 응답

같은 세션의 동시 API 요청을 단일 요청으로 직렬화할 필요는 없다. 다만 모든 인증 성공
응답이 쿠키를 갱신하므로 로그인·로그아웃 경계에서는 진행 중인 요청과 응답을 조율해야 한다.

- 같은 브라우저 프로필의 탭에 인증 전환 시작을 공유하고 새 보호 요청·자동 폴링을 멈춘다.
- 진행 요청의 응답 헤더 처리를 마친 뒤 로그아웃 또는 새 로그인 이동을 시작한다.
  fetch 취소만으로 서버 처리나 쿠키 적용이 취소됐다고 가정하지 않는다.
- 로그아웃 응답 처리가 끝나기 전에 새 로그인을 시작하지 않는다.
- 로그인 완료 후 본인 계정을 다시 조회하고 최신 인증 전환의 결과만 화면에 반영한다.
  여러 탭의 전환 조율은 공유 잠금·알림 등 실제 브라우저에서 동작하는 방식으로 구현한다.

늦은 일반 응답이 이전 ID를 다시 설정하거나 늦은 로그아웃이 새 쿠키를 지울 수 있다.
브라우저 Set-Cookie에는 조건부 비교·교체가 없어 JS의 응답 무시만으로 이를 막을 수 없다.
조율을 벗어난 새 탭·중단 상황에서는 재로그인이 필요할 수 있으며, 새 ID를 자동 복구한다고
보장하지 않는다. 서버에서는 이전 ID가 새 활성 세션을 인증·연장·폐기할 수 없어야 한다.
동일 ID 응답 순서가 뒤바뀌면 쿠키 만료가 조금 앞당겨질 수 있지만 서버 만료를 늘리지는 않는다.

## 로그아웃과 Content

`POST /auth/sessions/revoke`를 본문 없이 호출한다. session_revocation의 confirmed·
not_requested·rejected·unconfirmed를 구분하고 폐기 미확인을 완전한 성공으로 표시하지 않는다.
필드·상태는 [BFF 제공 API](API.md#로그아웃-응답)를 따른다.

Content의 If-Match·X-Save-Id·409 충돌 처리·Location·검색 인코딩은
[Content 제공 계약](CONTENT_API.md)을 따른다. 쿠키 왕복·만료 경계·
활동 연장·탭 전환·늦은 응답·장애는 실제 브라우저로 검증해야 한다.
