# BFF 로그인 연동

> **책임:** 로그인 시작·콜백·동의 완료의 처리 순서와 OAuth 임시 쿠키를 정한다.
>
> **확인할 때:** Google 페이지 이동과 Auth 로그인 호출을 연결할 때.

외부 로그인 시작과 Google callback은 BFF가 받는다. 로그인 완료와 동의 대기를 아래 순서로 연결한다.

1. **로그인 시작:** `GET /auth/oauth/google/prepare` 요청을 받으면 같은 경로의 Auth POST API에 로그인 준비를 요청한다.
   응답에 따라 브라우저 연결용 임시 쿠키를 설정하고 Google 로그인 URL로 리다이렉트한다.
2. **콜백 전달:** Google에 등록할 콜백 경로는 BFF의 `/auth/oauth/google/callback`로 한다.
   브라우저가 돌아오면 `code`·`state` 또는 로그인 오류와 임시 쿠키의 값을 Auth에 전달한다.
   BFF는 GET으로 받고 Auth의 같은 경로에는 POST로 전달한다.
3. **결과 분기:** `TERMS_REQUIRED`이면 아래 동의 대기로 연결한다. `AUTHENTICATED`이면 세션 ID를 [인증 쿠키](../BROWSER_SECURITY.md#세션-쿠키)로
   설정하고, 성공·실패 모두 [고정 프론트 주소](../API.md#로그인-후-고정-주소로-복귀)로 복귀시킨다.

BFF는 서버에 사용자별 임시 상태를 저장하지 않는다. 검증은 [Auth 로그인 흐름](../../../loresentry-authentication/docs/login/LOGIN_FLOW.md),
콜백 URL은 [Google 요청 설정](../../../loresentry-authentication/docs/API_CALLS.md#google-요청-설정)을 따른다.

## OAuth 임시 쿠키

| 항목 | 설정 |
|---|---|
| 이름 | HTTPS 환경은 `__Host-ls_oauth` |
| 값 | Auth가 반환한 `login_request_id` |
| 속성 | `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, Domain 생략 |
| 수명 | Auth의 `expires_at`까지 남은 시간, 최대 300초 |
| 로컬 HTTP 예외 | 로컬 프로필의 localhost·루프백에서만 `ls_oauth`, `Secure=false` |

Google의 최상위 GET 콜백에서 쿠키를 전달할 수 있도록 `SameSite=Lax`를 사용한다.
환경별 예외는 명시적인 프로필 설정으로 제한하고, 전달받은 임의 헤더로 Secure 여부를 결정하지 않는다.
새 로그인 시작은 기존 임시 쿠키를 교체한다. 동일 브라우저 프로필의 동시 로그인 흐름은 지원하지 않으며,
시도가 겹쳐 실패하면 로그인을 다시 시작한다. 다른 기기·브라우저의 OAuth 임시 흐름은
독립적이지만, 같은 계정의 새 로그인 성공은 기존 활성 세션을 교체한다.

콜백 응답의 `login_request_consumed=true`이면 발급 시와 같은 범위로 `Max-Age=0`을 설정한다.
미검증 콜백이나 통신 실패로 소비 여부가 확인되지 않으면 쿠키를 지우지 않고 최대 5분의 만료에 맡긴다.
이렇게 하여 잘못된 `state`를 가진 콜백이 현재 진행 중인 로그인 쿠키를 지우지 않게 한다.

## 약관 동의 연동

Auth가 계정 생성·조회 뒤 동의 여부를 판단하고, BFF는 그 결과에 맞춰 브라우저 상태를 연결한다.
내부 요청 구성은 [Auth 호출](../API_CALLS.md#약관-동의-호출), 외부 응답은
[동의 API](../API.md#약관-동의-api), 쿠키 속성은
[동의 대기 쿠키](../BROWSER_SECURITY.md#동의-대기-쿠키)를 따른다.

1. 콜백의 `AUTHENTICATED`이면 기존 로그인 완료 처리를 하고 남은 동의 쿠키도 삭제한다.
2. `TERMS_REQUIRED`이면 내부 응답의 ID·만료를 검증하고 동의 쿠키를 설정한다.
   OAuth 쿠키는 기존 소비 결과에 따라 정리하고, `result=terms_required`로 고정 프론트 주소에 복귀한다.
   이 분기에서 새 로그인 쿠키를 발급하거나 기존 로그인 세션을 폐기하지 않는다.
3. 약관 조회는 동의 쿠키로 Auth에 요청한다. 기존 로그인 세션의 검증·활동 연장은 수행하지 않는다.
4. 동의 완료는 CSRF·입력·동의 쿠키를 확인한 뒤 Auth에 요청한다. 세션 발급 성공 응답을
   검증한 경우에만 로그인 쿠키를 설정하고 동의 쿠키를 삭제한다.
5. 동의 API의 `CONSENT_REQUEST_INVALID`에는 대기 쿠키 삭제 헤더를 보낸다.
   버전 불일치·장애·결과 불명에는 쿠키를 그대로 두고 외부 오류를 반환한다. 자동 재전송하지 않는다.

화면·탭 닫기에 대응하는 서버 요청은 없다. 새 Google 로그인이 동의를 요구하면 새 대기 쿠키로
교체하며, 이미 동의한 계정이면 로그인 완료 후 대기 쿠키를 삭제한다. 새 로그인의 계정 선택에
이전 대기 쿠키를 사용하지 않는다. 이전 서버 대기의 만료는 Auth가 관리한다.
모달 닫기·복귀·오류별 화면 동작은 [프론트 동의 계약](../FRONTEND_AUTH_CONTRACT.md#약관-동의)을 따른다.

## 검증 범위

ID·만료 응답과 로그인 성공·취소·실패, 임시 쿠키 정리, 고정 주소 복귀를 검증한다. 실제 Google 동의 화면과 브라우저 쿠키 왕복은 별도 검증 대상이다.
복귀 후 본인 계정 조회와 인증 전환 순서는 [프론트 인계](../FRONTEND_AUTH_CONTRACT.md)를 따른다.

동의 연동은 다음 항목을 검증한다.

- 콜백 분기별 쿠키·고정 주소, 내부 ID 비노출과 동의 대기로 일반 보호 API 접근 불가.
- 조회·새로고침 시 쿠키 수명 유지, 쿠키 부재·중복·형식 오류, 완료 POST의 CSRF 실패.
- 원문 변경·만료·동시 완료·응답 유실에 대한 API 오류와 쿠키 처리.
- 모달 닫기에 서버 요청이 없고 새 로그인에서 새 Google 신원에 맞는 쿠키가 설정되는지 확인.
- 미선택 체크박스, 원문 재조회 후 체크 해제, 완료 뒤 본인 계정 조회와 서비스 이동.
