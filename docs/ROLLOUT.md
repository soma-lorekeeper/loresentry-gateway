# Auth·BFF 배포와 복구

> **책임:** 인증 관련 서비스의 호환성을 확인하고 배포·롤백·저장소 복구 절차를 정한다.
>
> **확인할 때:** 인증 계약을 변경해 배포하거나 이전 버전·저장소를 복구할 때.

설정·권한·접근 제한은 [운영 설정](OPERATIONS.md), 저장 형식과 동시성은
[Auth 세션 계약](../../loresentry-authentication/docs/session/SESSION_DESIGN.md)을 따른다.
실제 배포 상태와 일회성 전환 작업의 진행·완료 근거는 해당 이슈에서 관리한다.

## 배포 전 확인

1. 대상 Auth·BFF·프론트 버전의 내부 API·세션 저장 형식·쿠키·오류 처리 호환성을 확인한다.
2. [통합 도구](../integration/session/README.md)로 로그인·활동 연장·교체·폐기와 장애를 검증한다.
3. 실제 브라우저의 Google 왕복·쿠키와 [프론트 인증 전환](FRONTEND_AUTH_CONTRACT.md#인증-전환과-늦은-응답)을 확인한다.
4. 운영 Redis 자격 증명·ACL·TLS·네트워크 접근 제한·시각 동기화·관측 상태를 확인한다.

## 약관 동의 활성화

1. Auth의 `AUTH_TERMS_ENABLED=false`를 유지한 채 V3 스키마와 새 콜백 응답 코드를 먼저 배포한다.
   기존 BFF는 추가 `status`를 무시할 수 있지만 새 BFF는 `status`를 필수로 검사하므로 Auth보다 먼저 배포하지 않는다.
2. 동의 분기·쿠키·API를 처리하는 BFF와 모달·새 계정 조회를 처리하는 프론트를 배포한다.
   Auth의 동의 대기 키 권한을 확인한다. BFF Redis 권한은 늘리지 않는다.
3. 확정한 최초 원문을 새 Flyway 버전의 INSERT로 등록한다. 공개·시행 시각은 같은
   트랜잭션의 `CURRENT_TIMESTAMP`이며 로컬 테스트 날짜·초안을 운영 원문으로 사용하지 않는다.
   등록된 한국 날짜와 원문에 맞춰 공개 정책 페이지를 함께 게시한다.
4. 실제 Google 왕복·동의 API·공개 링크를 확인한다. 로그인 진입을 제한한 상태에서
   모든 Auth 인스턴스에 `AUTH_TERMS_ENABLED=true`를 적용하고, 비활성 인스턴스가
   로그인 요청을 처리하지 않는 것을 확인한 뒤 진입을 재개한다. 활성화 상태에서 원문이 없으면 로그인은 실패해야 한다.
   기존 로그인 세션은 그대로 유지하며 다음 로그인부터 최신 동의를 요구한다.

원문은 [Auth 등록 규칙](../../loresentry-authentication/docs/account/TERMS_CONSENT_DESIGN.md#1-약관-원문과-동의-기록)을 따른다.
기능 장애를 이유로 운영 동의 검사를 임의로 끄면 미동의 로그인도 허용된다.
활성화 이후의 복구는 로그인 진입을 제한하고 호환 버전을 복구하는 방식으로 진행한다.
적용한 Flyway 이력·공개 원문·사용자 동의 기록을 되돌려 수정하지 않는다.

## 온보딩·회원 탈퇴·샘플 프로젝트

BFF는 계정 응답의 `onboarding_completed`를 필수로 검사하므로 Auth의 온보딩 컬럼·응답과
계정 삭제 API를 먼저 배포한다. Content의 `DELETE /users/me/data`·`POST /projects/sample`도 BFF보다
먼저 배포한다. 이후 BFF, 마지막으로 온보딩·탈퇴 화면을 사용하는 프론트를 배포한다.
BFF를 되돌릴 때는 새 화면을 먼저 되돌리며, Auth·Content의 추가 API는 이전 BFF와 호환된다.

## 인증 계약이 호환되지 않는 변경

기존 로그인을 유지할 수 있는지 먼저 판단한다. 유지할 수 없다면 재로그인 영향을 알리고
다음 순서로 배포한다.

1. 인증·보호 API 트래픽을 제어하고 기존 인스턴스의 진행 요청을 배출한다.
2. 호환되는 Auth·BFF·프론트 버전으로 교체하고 이전 인증 경로가 요청을 처리하지 않는지 확인한다.
3. 적용할 쿠키·키 형식만 인증에 사용한다. 이전 형식으로 우회 인증하는 fallback은 추가하지 않는다.
4. 새 로그인·이전 로그인 차단·활동 연장·현재 로그아웃·이전 ID의 새 세션 폐기 불가를 확인한다.
5. 저장소 장애의 503·쿠키 미변경·내부 호출 차단을 확인한 뒤 트래픽을 재개한다.

쿠키 이름을 바꾼다면 이전 쿠키의 일회성 삭제를 전환 이슈에 명시하고, 발급과 같은
이름·Path·Domain 범위로 삭제한다.
이전 저장 키는 기존 TTL로 정리하며 Redis 전체를 flush하지 않는다.
이미 인증된 요청·열린 스트림은 세션 폐기만으로 취소되지 않는다.

## 롤백과 저장소 복구

Auth·BFF·프론트의 호환성을 확인하고 필요한 버전을 함께 되돌린다.
구버전이 이전 자격 증명·저장 상태를 다시 허용할 수 있다면 트래픽을 제어하고
영향 범위를 정해 폐기·재인증한 뒤 복구한다. 세션 ID를 이전 인증 형식으로 변환하지 않는다.

저장소 유실은 재로그인으로 처리한다. 과거 스냅샷의 세션을 그대로 활성화하면 이미 폐기된
로그인이 부활할 수 있으므로, 복구 시 세션 키의 범위 제한 정리·새 네임스페이스 등
재인증 방안을 정하고 확인한다. 데이터 복구·키 폐기는 영향 범위를 확인한 실행 작업으로 수행한다.

복구 후에도 배포와 같은 로그인·연장·교체·폐기·장애 동작을 확인하고 실제 결과를 이슈에 기록한다.
