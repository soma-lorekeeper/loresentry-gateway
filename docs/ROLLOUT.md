# Auth·BFF 단일 세션 ID 전환

2026-09-26 목표 절차다. 문서만 변경했으며 코드·설정·운영 전환은 미실행이다.
[세션 원본](../../loresentry-authentication/docs/session/SESSION_DESIGN.md)과
[운영 준비](OPERATIONS.md)를 기준으로 Auth·BFF·프론트를 함께 전환한다.

## 준비

1. Auth의 ID 생성·두 인덱스·로그인 결과·조건부 폐기를 구현한다.
2. BFF의 단일 쿠키·원자적 세션 검증/연장·새 외부 API·오류·쿠키 수명 갱신을 구현한다.
3. 프론트의 로그인 확인·세션 오류·새 로그아웃 API와 인증 전환 요청 조율을 구현한다.
4. 실제 Redis·Valkey 및 BFF 두 인스턴스에서 경쟁·만료·장애·ACL을 검증한다.
5. 실제 브라우저의 Google 왕복·쿠키 연장·탭 전환·늦은 응답을 검증한다.
6. GitOps·Secret·별도 Auth/BFF ACL·NetworkPolicy·시각 동기화·관측 설정을 준비한다.

## 공동 전환

인증 저장소·브라우저·내부 API가 바뀌므로 기존 로그인을 자동 승계하지 않는다.

1. 전환 시간과 재로그인 영향을 알리고 인증·보호 API 트래픽을 제어한다.
2. 구 인스턴스의 진행 요청을 배출하고 새 계약의 Auth·BFF·프론트로 교체한다.
3. 구 인스턴스·이전 인증 경로가 더 이상 요청을 처리하지 않는지 확인한다.
4. 새 쿠키·새 키 네임스페이스만 인증에 사용하고 이전 쿠키·저장 형식은 fallback으로 읽지 않는다.
5. 새 로그인, 이전 로그인 차단, 활동 연장, 현재 로그아웃, 이전 ID로 새 세션을 폐기하지 못함을 확인한다.
6. 저장소 장애에서 503·쿠키 미변경·내부 호출 차단을 확인한 뒤 트래픽을 재개한다.

이전 쿠키 이름의 일회성 정리는 구현 전환 목록에서 명시하고 발급과 같은 범위로 삭제한다.
이전 저장 키는 기존 TTL로 정리하며 Redis 전체를 flush하지 않는다.
이 절차는 기존 로그인 유지나 무중단을 보장하지 않는다. 이미 인증된 요청·열린 스트림
취소는 별도 기능이며 세션 폐기만으로 취소됐다고 판단하지 않는다.

## 롤백과 복구

Auth·BFF·프론트의 호환 버전을 함께 확인한다. 이미지 하나만 되돌리지 않는다.
구버전이 남은 이전 자격 증명·저장 상태를 다시 허용할 가능성을 검토하고, 트래픽을
제어한 상태에서 영향 범위를 정해 폐기·재인증한 뒤 복구한다.
새 세션 ID를 이전 인증 형식으로 변환하거나 검증을 우회하는 fallback은 추가하지 않는다.

저장소 유실은 재로그인으로 처리한다. 과거 스냅샷의 세션을 그대로 활성화하면 이미 폐기된
로그인이 부활할 수 있다. 복구 시 세션 키의 범위 제한 정리·새 네임스페이스 등 재인증
방안을 정하고 확인한다. 데이터 복구·키 폐기·배포는 별도 실행 작업이다.

## 완료 근거

새 코드 커밋·실행 환경·테스트 결과·브라우저 왕복·실제 ACL과 우회 차단·배포 상태를
새 기록으로 남긴다. `verification/`의 이전 실행 수치와 과거 브라우저 제외 결정을
이번 전환의 통과·검증 면제로 사용하지 않는다.
